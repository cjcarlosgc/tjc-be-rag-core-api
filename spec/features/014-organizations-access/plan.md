## Diseño técnico

- **Puertos con fakes en tests** (tokens de inyección; GitHub y Supabase reales solo en adapters productivos):
  - `SupabaseIdentityPort.getGithubIdentity(sub) -> { githubUserId, login? } | null` (`GET /auth/v1/admin/users/{sub}`, `identities[]` con `provider: 'github'`). Bajo `AUTH_BYPASS` (solo local/mock) se sustituye por una identidad sintética configurada (`AUTH_BYPASS_GITHUB_USER_ID`) y no se llama a Supabase. El handshake de `RealtimeGateway` resuelve la identidad por el mismo resolvedor que HTTP.
  - `GithubAccessPort`, con el installation token de la App. Cada lectura recibe una referencia `RepositoryRef = { installationId, repositoryName }` (`owner/repo`), porque las lecturas de GitHub se direccionan por `owner/repo` con el token de la instalación, y devuelve `GithubLookup<T> = { status: 'OK', value } | { status: 'NOT_FOUND' } | { status: 'NOT_INSTALLED' } | { status: 'UNVERIFIABLE' }`. Corte 4a (implementado): `getRepositoryOwner(repository) -> GithubLookup<{ repositoryId, ownerId, ownerLogin, ownerType }>` (devuelve también el `repositoryId` real, que el cliente no puede imponer) y `getRepositoryPermission(repository, githubUserId) -> GithubLookup<'admin' | 'maintain' | 'write' | 'triage' | 'read'>` (rol personalizado mapeado por su permiso base). Corte 2 (a agregar al mismo puerto con la misma convención de resultado): `listOrganizationInstallations()`, `getOrganizationMembership(orgId, githubUserId) -> { role, state }` y `listOrganizationOwners(orgId)`. `UNVERIFIABLE` (red, `5xx`, límite de tasa, instalación suspendida, `Members: read` ausente) es distinto de `NOT_FOUND` ("GitHub confirma que no existe o que no hay acceso") y de `NOT_INSTALLED` (el installation token responde `404`: la App ya no está instalada, p. ej. desinstalada): es la base de "conservar lo existente, negar lo nuevo". `NOT_INSTALLED` no es una caída: la organización deja de ofrecerse y sus Projects responden `404`, no un `503` permanente.
  - `GET /repos/{owner}/{repo}/collaborators/{username}/permission` se consulta por `login`: Core resuelve el login desde el `githubUserId` (`GET /user/{id}`) en cada verificación, sin caché, y no confía en el `githubLogin` guardado, que solo es presentación; así un login renombrado o reasignado a otra persona nunca hereda el permiso del usuario original. Esta lectura y la de `Members: read` son criterios de aceptación contra GitHub real (`DEC-ORG-001`, precondición 2).
  - Regla de acceso a un Project de organización: `GET /orgs/{org}/memberships/{login}` da membresía activa y rol de owner en una sola lectura; si no es miembro activo se deniega sin consultar el permiso del repositorio, aunque tenga `write` como colaborador externo (repositorios privados, internal o públicos); si es miembro, `getRepositoryPermission` define Maintainer/Reader; el owner es Admin.
- **Predicado de acceso:** `accessibleProject(userId, minRole)` sustituye a `ownedProject()` (ver `persistence`): Project personal = `ownerUserId` (rol `ADMIN`, sin registro ni GitHub); Project de organización = registro de acceso suficiente Y (binding no `REVOKED` o rol `ADMIN`), evaluado en cada petición y con prueba (no depende de que el paso a `REVOKED` haya borrado registros). `ProjectAccessService.require(userId, projectId, minRole)` cubre el borde de cada petición: personal ajeno -> `404`; organización con registro suficiente -> continúa; registro insuficiente -> `403`; sin registro -> verificación viva y alta, o `404`/`503`.
- **Default-deny obligatorio:** el guard de acceso exige que toda ruta autenticada declare su rol mínimo (`@RequireProjectRole('MAINTAINER')`) o una excepción explícita (`@NoProjectRole('<motivo>')`, para `GET /workspaces`, `POST /projects`, discovery, etc.); una ruta sin declaración falla al arrancar o en la petición. Una prueba enumera el router de Nest y falla ante cualquier ruta sin declaración; la matriz de INTEROP §6.13 es su fuente.
- **Alta de acceso sin carreras:** la verificación viva y el upsert de `project_access` se serializan con UN advisory lock transaccional por `(projectId, userId)`, el único mecanismo; las reverificaciones (`ACCESS_REVERIFY`, reconciliación) y las revocaciones toman el mismo lock. Retiene una conexión de base de datos durante las llamadas a GitHub, acotado por el presupuesto de verificaciones por petición. Los eventos que llegan durante un alta siempre encolan un `ACCESS_REVERIFY` que corre después y verifica en vivo. Invariante: un alta no sobrescribe ni recrea una revocación posterior al inicio de su verificación.
- **Presupuesto de verificaciones:** tope de concurrencia y presupuesto de llamadas a GitHub por petición (candidatos de `GET /projects`, `GET /workspaces`); agotado, los candidatos restantes se tratan como no verificables. No se memoizan denegaciones (sin caché, a petición del usuario). Riesgo residual aceptado por escrito: un límite de tasa de GitHub degrada las altas nuevas (omitidas o `503`), nunca revoca lo ya registrado.
- **Webhooks:** el ingress (`github-webhooks.service.ts`) enruta `member`, `membership`, `organization`, `team` y `repository` a un manejador de acceso que solo encola un job `ACCESS_REVERIFY` con el alcance seleccionado (`userId`/`githubUserId`, `repositoryId` u `organizationId`) y responde `202`. Los eventos de acceso no dependen de `binding.status`. `installation`/`installation_repositories` se amplían para borrar registros según INTEROP §6.9. Los eventos que no producen trabajo no persisten `WebhookDelivery` (como hoy `installation`) porque reverificar es idempotente. Los eventos `repository` (renombre, transferencia, eliminación) actualizan el binding de cualquier Project, incluidos los personales.
- **Jobs `ACCESS_RECONCILIATION` y `ACCESS_REVERIFY`** sobre `jobs`, que no tiene columna de alcance: columna `dedupeKey` (texto, nullable) e índice único parcial `WHERE status = 'PENDING' AND "dedupeKey" IS NOT NULL` (SQL en la migración), es decir, solo filas `PENDING`, no `RUNNING`. La siguiente ocurrencia de `ACCESS_RECONCILIATION` (`now + 1 h`) se encola AL INICIO de su ejecución sin chocar con su propia fila `RUNNING`, de modo que un fallo o una caída no rompe la cadena; un evento que llega durante un `ACCESS_REVERIFY` `RUNNING` encola uno nuevo (el reclamo no toma un `PENDING` cuya `dedupeKey` coincide con un `RUNNING` no obsoleto, así corre después); reclamo de locks obsoletos; la siembra al arrancar omite solo si existe un `PENDING` o un `RUNNING` no obsoleto; un `ACCESS_REVERIFY` no verificable se reprograma con backoff creciente acotado a una hora (sin consumir `maxAttempts`). La reconciliación reutiliza la lógica del alta, recalcula los registros de los Projects de organización que los tienen y revalida propietario y nombre del repositorio de todo Project vivo con binding, personales incluidos (transferido o eliminado -> `REVOKED`, y al pasar a `REVOKED` se borran los registros Maintainer y Reader; renombrado -> actualiza el nombre).
- Reverificación (corte 5b, sin cambio de contrato): `dedupeKey` por alcance del evento (`ACCESS_REVERIFY:<alcance>:<ids>`: usuario+repositorio, usuario+organización con o sin restricción a Projects con repositorio, repositorio, organización con repositorio) en lugar de por `(projectId, userId)`, para que el ingress no consulte registros ni GitHub; el job recorre los pares `(Project, usuario)` candidatos y toma el advisory lock de cada uno. Reprograma siempre el alcance COMPLETO (un evento nuevo del mismo alcance se absorbe en el `PENDING`), y un evento absorbido en un `PENDING` en backoff lo adelanta a ahora. La reconciliación corre (a), (c), (b) para corregir antes el nombre del repositorio que (b) usa para leer permisos.
- **WebSocket:** `RealtimeGateway` mantiene un mapa socket -> `Project` de sus suscripciones; verifica rol Reader al unir una sala (y devuelve `SubscribeAck`); un evento interno saca los sockets del usuario del Project cuando se borra su registro de acceso, el Project se borra lógicamente o deja de ser visible para él (binding `REVOKED` y no Admin); una verificación no disponible rechaza la suscripción con `GITHUB_VERIFICATION_UNAVAILABLE` y `retryable: true`.
- **Migraciones Prisma** (una por corte, sin backfill: la base está vacía): `user_github_identities` (corte 1); `projects.githubOrgId/githubOrgLogin` + check (corte 2); `project_access` + enum `ProjectRole` (corte 3); `jobs.dedupeKey` + índice único parcial de jobs de acceso (corte 5a).
- **Límites conocidos (cierre del ciclo de corrección 1 del bundle B; no cambian el contrato):** (a) `findUnseenOrganizationProjects` toma 51 candidatos ordenados por `createdAt` descendente, así que un miembro sin permiso sobre los 50 Projects más recientes puede no ver en `GET /projects` uno más antiguo al que sí accede (le queda el deep link, que da de alta el acceso); (b) `GET /workspaces` verifica solo las primeras 50 instalaciones ordenadas por login (el resto se trata como no verificable); (c) la reconciliación (b) comprueba el presupuesto por Project completo, no dentro de un Project (un Project con más registros que el presupuesto se procesa entero). Además, un listado de GitHub que alcanza el tope de páginas (10 x 100) o una lista de owners vacía con `200` son `UNVERIFIABLE`, nunca una ausencia confirmada.
- **Escala:** listar instalaciones de la App y verificar la membresía por organización es aceptable a escala de tesis; no se agrega caché de permisos. Si la latencia de `GET /workspaces` se vuelve un problema con la App pública, se evalúa una caché corta solo de la lista de instalaciones (nunca de accesos) en una decisión aparte.

## Cortes de implementación

1. **identidad GitHub + identidad.** `SupabaseIdentityPort`, tabla `user_github_identities`, resolución perezosa del `githubUserId` tras validar el JWT (HTTP y handshake WebSocket), identidad sintética de `AUTH_BYPASS`, `401 GITHUB_IDENTITY_REQUIRED` y `503 IDENTITY_UNAVAILABLE`. Sin cambio de rutas. Actualiza `012-web-authentication`.
2. **Project organizacional + workspaces (paso de integración; no se publica solo).** `GET /workspaces` (personal y organizaciones; ante una caída de GitHub degrada a solo el personal: el respaldo de organizaciones con acceso registrado llega con el corte 3), `workspaceId` (solo personal) en `POST /projects` y `GET /projects`, `PATCH /projects/{id}`, `workspace` y `role` en `ProjectResponse`, columnas de organización, `GithubAccessPort` del lado de organización. Hasta el corte 3 NINGUNA ruta acepta un `workspaceId` de organización (`404 WORKSPACE_NOT_FOUND`) y `POST /projects` solo crea personales; el predicado sigue siendo el creador (`ownerUserId`) y `role` es `ADMIN`, el comportamiento final para Projects personales. La creación en organización, el filtro de discovery por organización, el respaldo de `GET /workspaces` con organizaciones de acceso registrado y todo lo compartido entran con el corte 3.
3. **acceso automático + roles derivados + binding autorizado parte 4b (roles).** `project_access` (solo Projects de organización), `accessibleProject`, `ProjectAccessService`, alta al entrar sin carreras, membresía activa siempre, roles Admin/Maintainer/Reader, default-deny y `403 PROJECT_ROLE_INSUFFICIENT` en toda la matriz, creación de Projects en organización, `workspaceId` de organización en discovery y `POST /projects`, rama de organización de `REPOSITORY_OUTSIDE_WORKSPACE` y rol Maintainer en binding/`enable`/pausa, binding `REVOKED` visible solo a Admin, listados omitiendo lo no verificable, `503 GITHUB_VERIFICATION_UNAVAILABLE`, WebSocket. Migra todos los repositorios que usan `ownedProject`.
4a. **binding autorizado parte 4a (la corrección de seguridad, primero).** Validación de propietario y permiso en `POST .../integrations/github` (personal: propietario del repositorio = creador; permiso `maintain`/`write`/`admin`), en `verify-app-access` y `branches`, y `workspaceId` (solo el personal) en el discovery, con el orden de validación de INTEROP §6.8 y `503` ante permiso no verificable. Solo necesita la identidad del corte 1 y `GithubAccessPort.getRepositoryPermission`/`getRepositoryOwner`; NO necesita `project_access` ni roles. Se implementa y publica justo tras el corte 1.
5. **revocación de acceso.** Se divide para paralelizar. **5a** (implementado sobre el corte 3 ya fusionado, así que incluye el borrado de registros al pasar un binding a `REVOKED`): `repository.renamed`/`transferred`/`deleted` sobre el binding de cualquier Project (nombre o `REVOKED`), `installation`/`installation_repositories` sobre bindings, el borrado de los registros Maintainer y Reader (con `ProjectAccessService.revoke` y la expulsión de sockets de `ProjectSubscriptionsService.revalidateProject`) al pasar un binding a `REVOKED` por esas vías o por la reconciliación (c), infraestructura de jobs (`dedupeKey`, índice parcial solo `PENDING`, reclamo de locks obsoletos, autoprogramación al inicio, siembra, backoff) y la revalidación de propietario y nombre del binding en la reconciliación (c), personales incluidos. **5b** (depende del 3 y del 5a): todo lo que recalcula `project_access` o usa `projects.githubOrgId/githubOrgLogin` para acceso de usuarios: `member`, `membership`, `team`, `organization` (`member_removed`, `renamed`, `deleted`), `repository.privatized`, `ACCESS_REVERIFY`, reconciliación (a) y (b), el ciclo de vida de la organización y el borrado por desinstalación de la App de una organización (incluidos los Admin). Ante una revocación interrumpida el predicado del corte 3 (binding `REVOKED` -> solo Admin) protege por sí solo y la reconciliación (c) termina el borrado.

## Dependencias entre cortes y trabajo en paralelo

```text
1 ──┬──> 4a ──┬──> 3 ──> 5b
    │         └──> 5a ──> 5b
    └──> 2 ─────> 3
```

- 4a depende de 1 (identidad). 2 depende de 1 (`githubUserId` para el workspace personal y la verificación de owner). 3 depende de 2 (columnas de organización y `role` de `ProjectResponse`) y de 4a (extiende su validación con la rama de organización y el rol). 5a depende de 4a (`getRepositoryOwner`) y no de 2 ni de 3 porque los efectos que usan columnas de organización o `project_access` se movieron al 5b. 5b depende de 3 (y con él de 2) y de 5a (infraestructura de jobs).
- Dos desarrolladores: tras el corte 1, A implementa el 4a (seguridad primero) y B el corte 2; ambos extienden `GithubAccessPort` con métodos distintos sobre una interfaz acordada. Luego A toma el corte 3 (`project_access`, predicado, alta sin carreras) y B el 5a (jobs y sincronización de binding); al fusionar el 3, B sigue con el 5b (registros de acceso y eventos de organización). Los conflictos de esquema Prisma se evitan porque cada corte tiene su propia migración; solo comparten `github-webhooks.service.ts` (5a/5b) y `repository-bindings.service.ts` (4a/3).
- **Publicación:** bundle A = corte 1 + 4a, se publica primero y lo antes posible (la App no debe ser instalada por terceros, idealmente privada, hasta desplegarlo) y espera a que la Console solo GitHub esté publicada, porque `GITHUB_IDENTITY_REQUIRED` aplica a toda la sesión. Tras el sync de implementación del bundle B, y no antes, la Console envía `workspaceId` a `POST /projects` y `GET /projects` y consume `workspace`/`role` (los servidores rechazan campos no declarados). Bundle B = cortes 2 + 3 (con 4b) + 5 (5a y 5b), siempre juntos: dar acceso (3) sin poder revocarlo por evento (5) no es aceptable y los workspaces de organización sin roles no tienen uso. El corte 2 no se publica solo.
- **CONTRACT_SYNC:** una regla única: un sync de definición cuando se aprueba el contrato (lo emite el leader) y un sync de implementación por cada bundle desplegable (A y B). Nunca uno por corte.

- **Corte 4a:** `POST .../enable` sobre `REVOKED` con `repositoryId` distinto (`404`), repositorio transferido (`400`) y App recuperada (reactiva), orden de `branches` y `verify-app-access` con la App no instalada, orden de validación completo de `POST .../integrations/github` (personal), sin permiso -> `404` previo a `REPOSITORY_OUTSIDE_WORKSPACE`, permiso `read`/`triage` -> `403`, `verify-app-access` y `branches` con permiso suficiente, menor, ninguno y `UNVERIFIABLE` (`503`, nunca `NOT_AUTHORIZED` ni `404`), sin sondeo de repositorios ajenos (`REPOSITORY_ALREADY_BOUND` solo tras las validaciones de propietario y permiso), no revinculación, un Reader ya no obtiene respuesta de `verify-app-access`.
- **Corte 2:** workspaces (solo personal, con organizaciones, organización sin `Members: read`, GitHub caído), `workspaceId` de organización rechazado (`404`) en todas las rutas, `PATCH` (nombre válido, vacío, campo extra, no visible), `DELETE` como creador.
