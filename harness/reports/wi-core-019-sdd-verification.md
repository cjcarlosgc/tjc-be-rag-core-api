## 4. Ambigüedades reales

### 4.1 ADD VALUE del enum `ProjectRole` — no bloquea (propuesta de resolución)
Postgres 12+ permite `ALTER TYPE ... ADD VALUE` dentro de una transacción, pero el valor nuevo no se puede USAR hasta el commit. Prisma Migrate aplica cada archivo `migration.sql` como una sola ejecución (efectivamente transaccional en Postgres). Propuesta: archivo SOLO con `ALTER TYPE "ProjectRole" ADD VALUE IF NOT EXISTS 'WRITER' BEFORE 'READER';` (orden `ADMIN, MAINTAINER, WRITER, READER`, igual al `schema.prisma` y a la jerarquía). Ningún `UPDATE`, índice parcial, default ni `CHECK` que mencione `WRITER` en ese archivo ni en columnas del mismo archivo (el uso en código es posterior al commit). `rolesAtLeast` y los guards no dependen del orden del enum en Postgres, sino de `ROLE_RANK`; no comparar roles con operadores del enum SQL. El valor no se puede quitar: el rollback de la migración no existe (documentar). Verificar en el entorno local con `prisma migrate deploy` en una base con filas y que `prisma migrate diff` no detecte deriva por orden.

### 4.2 `ACCESS_REVERIFY` de alcance completo — no bloquea (propuesta de resolución), es trabajo del WI
Hoy NO existe con alcance completo: solo 5 alcances selectivos por evento, y la reconciliación horaria (b) recalcula todos los registros pero es otro job. El AC lo permite ("si no lo tiene, este WI lo añade"). Propuesta: nuevo alcance `ALL` (todos los `project_access` de Projects de organización vivos), `dedupeKey` `ACCESS_REVERIFY:ALL`, sembrado en `onApplicationBootstrap` con `enqueueDeduped(..., { skipIfRunning: true })` como la reconciliación. Punto abierto menor: "al desplegar" = en cada arranque. Es idempotente (dedupe sobre `PENDING`/`RUNNING` no obsoleto) pero cuesta una pasada por arranque; alternativa: encolar solo si existe algún registro `MAINTAINER` sin reverificación posterior al valor `WRITER` (requiere marca) -> más complejidad; se recomienda el arranque simple, con la pasada acotada por `ACCESS_VERIFICATION_CONCURRENCY` y el presupuesto de GitHub. Documentar la elección en `plan.md` (Corte SMART V3).

### 4.3 Rol registrado mientras tanto — no bloquea
`reverify()` conserva el registro cuando GitHub es `UNVERIFIABLE` (backoff, sin degradar), y el job reprograma el alcance completo. Mientras no se reverifique, un usuario con `write` conserva `MAINTAINER` y puede seguir respondiendo preguntas funcionales; es el comportamiento aprobado ("conserva el rol registrado, sin degradación silenciosa"), pero constituye una ventana de autoridad mayor a la de DEC-ORG-003. Propuesta: aceptarla y registrarla como riesgo residual; el acceso nuevo ya nace con el rol correcto. No hay decisión que cerrar.

### 4.4 Reverificación de acceso del rol Writer — no bloquea (propuesta)
Las verificaciones usan `deriveRole` -> `roleForPermission`; solo falta que devuelva `WRITER` para `write`. Cuidados: (i) la reconciliación (b) y `reverify` deben tratar `MAINTAINER -> WRITER` como UPDATED (cambia sockets), no como revocación; (ii) `binding-lifecycle`/webhooks que borran "Maintainer/Reader" deben borrar también `WRITER` (hoy usan `role != ADMIN`, ya cubre); (iii) predicado `accessibleProject` rama 3 con `rolesAtLeast(min)` ya incluye WRITER; (iv) realtime/`SubscribeAck` enumera roles. Sin ambigüedad de spec.

### 4.5 `sourceRef` sin escritor — no bloquea (propuesta)
`APPROVED_IMPORT` no se crea hoy en ninguna ruta (grep sin resultados fuera de enums). El AC pide persistir `sourceRef` "solo para APPROVED_IMPORT": propuesta, columna nullable y validación de invariante en el repositorio (`sourceRef` no nulo solo si `source=APPROVED_IMPORT`) sin crear flujo de import. Si el usuario esperaba un flujo de import en este WI, hace falta confirmarlo (no está en las HU/AC).

### 4.6 `ConfirmingRole` como enum de base de datos — no bloquea (propuesta)
El AC dice «enum ConfirmingRole ADMIN|MAINTAINER». Propuesta: enum Prisma `ConfirmingRole { ADMIN MAINTAINER }` para `FunctionalKnowledge.confirmedRole` (usar el mismo nombre que el tipo TS actual; la tabla de abstenciones de 018 usa `ProjectRole` y no se cambia). Rol del confirmante al responder: tomar `grant.role` (ya ADMIN o MAINTAINER, garantizado por el `require('MAINTAINER')`), reutilizando `confirmingRole()`.

## 5. Riesgos de datos y despliegue

- **R1 (alto, orden de despliegue):** el valor `WRITER` en la base con código viejo rompe la lectura (Prisma falla ante un enum desconocido). La migración ADD VALUE por sí sola no crea filas WRITER, pero la reverificación sí. Mitigación: desplegar migración + código A+B+C juntos; revertir código después de la reverificación dejaría filas WRITER ilegibles para el código anterior. Documentar en el cierre.
- **R2 (cambio observable):** usuarios con solo `write` pierden la capacidad de responder preguntas funcionales (y quedan Writer tras la reverificación). Es lo aprobado, pero requiere el Contract Sync a Console y la comunicación del cambio.
- **R3:** entre A y B, un Writer no satisface `MAINTAINER` en las rutas aún sin migrar: mismos commits en el mismo despliegue o B primero con código tolerante. Recomendado: A y B en el mismo ciclo de revisión.
- **R4 (concurrencia):** la reverificación ya usa el advisory lock por `(projectId, userId)`; el alcance `ALL` no debe inventar otro mecanismo ni mantener conexiones largas fuera del presupuesto por petición. Volumen: un job con todos los registros puede ser largo; el reclamo de locks obsoletos y el backoff existentes lo cubren, a verificar con una prueba de dedupe/`RUNNING`.
- **R5 (migración):** columnas de procedencia nullable, sin backfill; las reglas históricas quedan `null` y no deben fallar el mapeo ni el supersede. `originHeadSha` se toma de `run.headSha` en el momento de responder, también en `supersede`.
- **R6 (RLS):** las migraciones solo añaden columnas/enum; no hay tabla nueva, así que no se requiere RLS adicional.
- **R7 (seguridad):** cualquier ruta que siga en `MAINTAINER` por omisión no abre acceso; el riesgo es el contrario (olvidar un sitio y dejar a Writer sin acceso). La matriz e2e por ruta y rol (`access-matrix.e2e-spec.ts`) es la red de seguridad.
