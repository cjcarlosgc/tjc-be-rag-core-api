## Criterios de implementación recomendados

1. DTO público: UUID/forma válida de `analysisRunId`, ruta relativa y nombre calificado como texto no vacío según las validaciones de DTO del proyecto; `repetitions` mantiene el único valor permitido 3. `projectId` y `targetId` no se aceptan.
2. Guardia Writer sobre `analysisRunId`; resolver el Run de forma visible en servicio para conservar el mismo 404 que su GET. Validar `Idempotency-Key` de acuerdo con los errores de §4 y el patrón V3 ya usado por retrieval comparisons.
3. Exigir `run.projectVersionId`; cargar esa versión concreta y comprobar `COMPLETED`. Un Run sin versión todavía responde el error de conflicto existente `409 ANALYSIS_NOT_FINISHED`; no sustituirlo por la versión actual del Project.
4. Buscar el símbolo solo bajo `run.id` por el par exacto `(filePath, qualifiedName)`; si no existe, 404 contractual. Exigir kind `METHOD|FUNCTION` y `changeKind=DIRECTLY_CHANGED`; si no, 422 contractual.
5. Convertir el símbolo mediante `toRetrievalTarget` y resolver el `TestTarget` coincidente únicamente entre los targets de `run.projectVersionId`, con el mismo emparejamiento exacto que `findMatchingTestTarget`. Si el símbolo elegible no tiene TestTarget materializado en esa versión, no degradar a búsqueda por nombre en el Project ni a otra versión; tratarlo como inconsistencia/unresolvable target usando el error interno vigente que corresponda y añadir prueba.
6. Mantener precedencia funcional existente de soporte de framework: comprobar `detectedFramework ∈ JEST|VITEST|PHPUNIT` y aplicar `422 UNSUPPORTED_PROJECT` según §6.5.1; no reintroducir rechazo PHP tras WI-CORE-029. Mantener resolución de modelo, persistencia de `ExperimentRun`, scope `EXPERIMENT_CREATE`, transacción con job, replays sin segundo encolado, payload interno, estado y polling `202`.
7. Pruebas unitarias/HTTP deben fijar: DTO acepta V3 y rechaza forma heredada/extra; authorization por AnalysisRun y 404/403; Run sin versión o versión no completada; búsqueda exacta; faltante/no elegible; mapeo del target desde versión congelada cuando `currentVersionId` diverge; soporte de framework incluyendo PHPUnit; respuesta incluye `analysisRunId`; idempotency replay y creación atómica no duplican jobs.

## Propuesta / límite de interpretación

- La palabra “elegible” en el criterio del WI se interpreta con la regla contractual concreta: símbolo exacto `METHOD|FUNCTION` y `DIRECTLY_CHANGED`, con `ProjectVersion` asociada completada. No se añade una condición nueva de `AnalysisRun.current=true` ni se exige un estado terminal específico del Run: §6.5 no los declara; el endpoint análogo de retrieval tampoco los impone. Restringir a runs vigentes podría impedir reproducir comparaciones sobre evidencia histórica y sería un cambio de comportamiento no aprobado.
- Si no existe un `TestTarget` en el snapshot para un símbolo contractual elegible, el contrato no define explícitamente el código para esa inconsistencia interna. Esto no bloquea la especificación del flujo principal: mantener el error Core existente de target no resoluble, sin introducir un código público nuevo, y probar el caso; elevarlo a decisión solo si el comportamiento observado muestra que ese estado es alcanzable como condición normal del índice.
- No se necesita ampliar INTEROP ni publicar Contract Sync: el DTO de §6.5 ya es el objetivo canónico y el WI está declarado sin impacto contractual.

## Conclusión

`SPEC_VERIFIED`. El alcance tiene contrato canónico aprobado, subtarea enlazada y un patrón V3 local implementado para validación de Run/símbolo/idempotencia. La principal precaución es no usar el `currentVersionId` del Project ni confiar en `targetId` del cliente; ambos reabrirían la brecha que el WI corrige. No hay cuestión que requiera decisión adicional del usuario antes de delegar implementación.
