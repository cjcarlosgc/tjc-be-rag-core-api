## Definiciones
- **Captura**: registro por Project con estado `ARMED` (esperando), `RESERVED` (consumida por un Run) o `DISARMED` (desarmada a mano). Un Project tiene como máximo una captura `ARMED`.
- **Siguiente AnalysisRun elegible**: el primer AnalysisRun **nuevo** de ese Project creado **después** de armar, con `repositoryBindingEligible = true` y PR no borrador. No la consumen: un evento duplicado o un HEAD sin cambios (no crea Run), un borrador, un PR anterior al vínculo, eventos no elegibles, ni los Runs creados antes de armar. Un HEAD nuevo del mismo PR crea otro Run, que ya no se reserva (la captura está consumida); el Run reservado queda `OBSOLETE` como cualquier otro y la captura sigue `RESERVED` (hay que armar otra).

## Alcance (solo Core: `app/src`, migración aditiva, contrato aditivo, spec y pruebas)
1. **Datos (migración aditiva, sin backfill):** enum `ExperimentCaptureStatus {ARMED, RESERVED, DISARMED}`; tabla `experiment_captures` (`id` uuid, `projectId` FK, `status` por defecto `ARMED`, `armedByUserId`, `armedAt`, `reservedAnalysisRunId` nulo, `reservedAt` nulo, `disarmedByUserId` nulo, `disarmedAt` nulo, `createdAt`, `updatedAt`); **índice único parcial** `(projectId) WHERE status = 'ARMED'` por SQL en la migración (mismo patrón que el índice único parcial de reglas ACTIVE de FK y la prueba `*.pg.spec.ts` correspondiente); columna nullable `analysis_runs.experimentCaptureId` (FK, única). RLS y privilegios como el resto de las tablas del producto (copia el patrón de la migración más reciente que crea tablas).
2. **API (aditiva, INTEROP-2.25):** módulo `experiment-captures` (controlador, servicio, repositorio, DTO):
   - `POST /projects/{projectId}/experiment-captures` → `201 ExperimentCaptureResponse`; rol **MAINTAINER**; crea una captura `ARMED` con el usuario; si ya hay una armada, `409 EXPERIMENT_CAPTURE_ALREADY_ARMED` (retryable false). Sin `Idempotency-Key` (el índice único la hace segura).
   - `GET /projects/{projectId}/experiment-captures?cursor&limit` → `200 Page<ExperimentCaptureResponse>`, la más reciente primero; rol **READER**.
   - `DELETE /projects/{projectId}/experiment-captures/current` → `200 ExperimentCaptureResponse` (ya `DISARMED`); rol **MAINTAINER**; sin captura armada, `404 EXPERIMENT_CAPTURE_NOT_ARMED`.
   - `ExperimentCaptureResponse`: `{ captureId, projectId, status, armedBy, armedAt, reservedAnalysisRunId | null, reservedAt | null, disarmedBy | null, disarmedAt | null }` (fechas ISO-8601 UTC; `armedBy`/`disarmedBy` son ids de usuario).
   - Todas las rutas con el guard de roles existente (Project no visible ⇒ 404, rol insuficiente ⇒ 403); la matriz de rutas por rol (§6.13) y su prueba `default-deny` quedan al día.
3. **Reserva atómica:** en el embudo único de creación de Runs desde GitHub (`AnalysisRunsService.startRunFromWebhook`, que usan el webhook y el job de backfill de metadatos), cuando `isNew && repositoryBindingEligible === true && !draft`, **antes de devolver el Run** (y por tanto antes de que el llamador encole el job de snapshot): en una transacción, `UPDATE experiment_captures SET status='RESERVED', reservedAnalysisRunId=…, reservedAt=now() WHERE projectId=… AND status='ARMED'` y, si afectó una fila, `UPDATE analysis_runs SET experimentCaptureId=…`. Dos Runs concurrentes ⇒ solo uno reserva. Si el reservador falla de forma inesperada, se registra y el Run se crea **normal** (la captura sigue `ARMED`); la creación del Run nunca falla por la captura. Sin captura armada, el único coste es esa consulta/UPDATE sin filas.
4. **Run reservado sin Checks (D1):** `AnalysisRunChecksService.publishForRun` (embudo único de publicación de Checks) devuelve sin llamar a GitHub Integration cuando el Run tiene `experimentCaptureId`; `checkId` y `checkPublishedAt` quedan nulos. El resto del flujo es idéntico (indexación, símbolos, Functional Knowledge, `ACTION_REQUIRED`, Validation, estados, propuestas), de modo que `POST /experiments` funciona sobre el Run igual que hoy. No se añade ningún estado a `AnalysisRunStatus`.
5. **Respuestas de Run:** `AnalysisRunSummaryResponse` (y por herencia el detalle) gana `experimentCapture: { captureId: string; reservedAt: string } | null`, siempre presente (nulo si no hay). **Verificar** si el payload de tiempo real (`analysis-run:update`) reutiliza el resumen y si `schemas/realtime-events.schema.json` es estricto: si el campo lo rompe, o bien se excluye del evento o se amplía el esquema (decisión a reportar; el digest del árbol `schemas/` cambia solo en ese caso).
6. **Errores nuevos:** `EXPERIMENT_CAPTURE_ALREADY_ARMED` (409) y `EXPERIMENT_CAPTURE_NOT_ARMED` (404) en el enum `ErrorCode`, con su fila en la tabla de errores del contrato.
7. **Contrato (leader):** INTEROP-2.24 → **2.25**, aditivo y `breaking:false`: sección nueva para las tres rutas y su DTO, campo nuevo en las respuestas de AnalysisRun, filas de la matriz de roles, códigos de error, cabecera y registro de versiones. Sin cambio de SYSTEM salvo que la prueba de consistencia lo exija. Contract Sync publicado (consumidores: Console —UI, WI aparte—; Integration y Sandbox solo re-espejo documental, sin cambio de código).
8. **Spec (leader):** `spec/features/008-experimental-comparison` (sección HU18 con casos de aceptación), tasks (`ST-CORE-131`) y CHANGELOG.
